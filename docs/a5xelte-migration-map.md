# A5XELTE migration from the SWEET donor

The donor README and `NOTES.md` describe a demonstrated Redmi Note 10 Pro (`sweet`) iOS 16 port. They are source and sequencing references. This document is the Samsung SM-A510F decision record. `A5XELTE_PROGRESS.md` records build results, TWRP readback and user-visible behavior separately.

| Component | A5XELTE status | When to adapt or retire SWEET code |
| --- | --- | --- |
| BOOT handoff and loader | Samsung BOOT p10 with stock DTBH; Exynos7580 EL1 handoff and 4 KiB loader are device tested. | A5XELTE uses `shim/a5xelte/` now. Do not use Xiaomi `fastboot boot`, ABL/QCOM register writes or donor `shim/build.sh` on Samsung. Keep the donor files as a comparison until A5XELTE has an independently reproducible build and recovery path. |
| XNU page size and board target | A5XELTE XNU entered and executed an instruction after enabling the 4 KiB MMU. | `0082` onward provides the Samsung build path. Remove the temporary donor `SWEET` compile definition only after every shared compile-time facility has an A5XELTE replacement and the resulting kernel is built and reaches the same device checkpoint. |
| Early display and console | Exynos DECON/DSIM handoff, XNU assembly text, and dynamic C/`kprintf` text through CPU0 startup and HFS registration are visible on the phone. | Use `mainline/drivers/exynos7580-drm-handoff.c` for register/clock behavior. Keep the early display until a later XNU framebuffer service can take over. Do not import Qualcomm framebuffer or IOMFB assumptions. |
| Interrupts and timer | The phone and recovered kernel log report `4/4 CPUs initialized, SGI1 verified` on the first Exynos7580 cluster. The eight-core trial panicked on an unexpectedly owned ticket lock while registering the second cluster, so four cores remain the tested configuration. | Preserve the GICv2 SGI sender-bit fix and physical-counter path. Investigate second-cluster lock/timing separately from display performance; do not present eight-core startup as verified. |
| Built-in pthread provider | The A5 build previously omitted the donor's paired libpthread provider because its source guards selected only `ARM64_BOARD_CONFIG_SWEET`; the phone panicked at `pthread_shims.c:318`. Patch `0102` links the provider; the device screen confirms its registration and later network worker scheduling. | Keep this shared Apple libpthread source as a build dependency. Its `sweet_*` filenames describe donor provenance, not a Qualcomm hardware interface. |
| Storage and root | HFSX USERDATA p23 is the iOS root. The writable eMMC path and the separate `A5XLOG1` ring in the first 8,193 sectors of SYSTEM p20 are device verified by TWRP reads. | Keep root and log writes inside their respective GPT partitions. The donor's UFS driver and `fastboot flash userdata` instructions do not apply. |
| Input, display services and userland | The user's phone showed the Apple logo and iOS home screen; Home, Power and volume buttons respond, and patch `0123` delivered touch contacts that visibly control an iOS screen item. Recovered logs show SpringBoard and backboardd executing. The `AppleCLCD` bridge copies IOSurface pixels to the 1080×1920 DECON buffer on the CPU. Patch `0124` changes the A5 presentation cap from 10 to 30 Hz with measurements; device results are pending. Native Linux Panfrost support does not establish XNU/iOS Mali acceleration. | Preserve the working touch and DECON path. Measure frame-copy cost and service restart load, then adapt Exynos7580 G3D hardware support and the iOS rendering interface as separate GPU milestones. Do not label the CPU framebuffer as GPU-backed. |
| Documentation | README now labels the SWEET section as donor reference; this map and A5XELTE notes state current facts. | Update the A5XELTE README summary at each proven milestone. Keep donor `NOTES.md`, `docs/QEMU_TESTING.md` and donor examples intact as historical references until their replacements are tested, then move them under a donor-specific path in a dedicated cleanup commit. |

SWEET-specific files should be removed from the active A5XELTE build in stages: first remove hardware assumptions from the selected A5XELTE target; next confirm each replacement builds and boots to the previous checkpoint; finally remove unused donor files and rename compatibility symbols. Deleting donor files before that loses working reference code and can hide build dependencies. The repository can retain donor history even after the A5XELTE default path is independent.
